MicroPython is Python, but on a machine with a few hundred kilobytes and no operating system around it. The language is familiar; what changes is time, memory and the shape of a program that must run for months.

The shape of a device program

# main.py
import time
from machine import Pin

time.sleep(2)                  # while developing: a moment to Ctrl-C in
led = Pin(2, Pin.OUT)

def step():
    led.value(not led.value())

while True:                    # a device program never ends
    try:
        step()
    except Exception as e:
        print("step failed:", e)   # log and carry on, don't die
    time.sleep_ms(500)

There's nothing to return to: when the loop ends, the device does nothing until reset. So the outer loop catches and logs, and anything that can hang (a network call) has a timeout.

Time

start = time.ticks_ms()
...
elapsed = time.ticks_diff(time.ticks_ms(), start)   # never  now - start

ticks_ms() wraps around, so subtracting goes wrong eventually; ticks_diff handles it. The real-time clock starts at 2000-01-01 after every power cut; set it from the network with ntptime.settime() (UTC) once Wi-Fi is up, before any timestamp means anything.

Memory

import gc
gc.collect(); print(gc.mem_free())
  • Allocate once, reuse: a growing list of readings, or string concatenation in a loop, ends in MemoryError after hours, not seconds.
  • The heap fragments: plenty free in total, no block big enough. Collect after big temporary objects (gc.collect()) and avoid building large JSON strings.
  • Boards with PSRAM have megabytes instead of ~100 KB free; the same code is far more forgiving there.

Doing several things: asyncio

import asyncio

async def blink():
    while True:
        led.value(not led.value()); await asyncio.sleep_ms(500)

async def report():
    while True:
        publish_reading(); await asyncio.sleep(30)

async def main():
    asyncio.create_task(blink())
    await report()

asyncio.run(main())

The same model as asyncio on your Mac: one thread, switching at await. A blocking call (time.sleep, a sensor read that waits 750 ms) stalls every task. Timers (machine.Timer) exist too, but their callbacks have the same limits as interrupts.

Storing a little data

The filesystem is in flash, which wears out after many thousands of writes per block. Writing a file every few seconds for a year is a problem; writing settings when they change is not. For small values, esp32.NVS is a key-value store built for it.

From FastAPI

The rules you learned for the event loop apply unchanged: one blocking call stalls everything. The difference is that here, "everything" includes the Wi-Fi keepalive and the watchdog.

Trap

readings.append(value) in the main loop, to "send later". After a day offline the list fills the heap and the device resets, losing it all. Keep a fixed-size buffer, or send and forget.

Try it

Write a main loop that blinks the LED with asyncio while another task prints gc.mem_free() every 10 s. Leave it an hour: is free memory stable?
