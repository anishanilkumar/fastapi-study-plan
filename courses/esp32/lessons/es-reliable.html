A device on your desk is watched; a device behind the fridge isn't. It must recover from anything by itself: a hung sensor, a router reboot, a bug that shows after three weeks. And you must be able to update it without taking it out.

The watchdog

from machine import WDT
wdt = WDT(timeout=30_000)        # reset the board if not fed for 30 s

while True:
    do_one_cycle()               # with timeouts on everything inside
    wdt.feed()
    time.sleep(10)

Once started, the watchdog can't be stopped: if the program hangs (a sensor read that never returns, a socket stuck), it resets the board. Feed it only from the main loop, after real work, never from a timer: a timer keeps firing even when the main loop is stuck, which defeats the point. Pick a timeout longer than the slowest healthy cycle, Wi-Fi connect included.

Know why it restarted

cause = machine.reset_cause()    # PWRON_RESET, HARD_RESET, WDT_RESET, DEEPSLEEP_RESET, SOFT_RESET
c.publish(b"home/kitchen/fridge/boot", str(cause).encode(), retain=True)

Publish the reset cause and an uptime counter. A device that's reset by its watchdog twice a day is telling you about a bug, and you'll only hear it if it says so.

Time

After every power cut the clock says 2000. Call ntptime.settime() after Wi-Fi connects (it sets UTC), and again every day or so; the ESP32's clock drifts. Until it has worked, publish without a timestamp, or not at all: a reading dated 2000-01-01 is worse than none.

Updating in place

  • ESPHome: OTA built in (previous lesson). The easy answer.
  • MicroPython code: over USB with mpremote, or have the device fetch new .py files from a server you control and reset. If you do that, download to a temporary name, check it (size, a hash), then rename, so a broken download never replaces a working file.
  • MicroPython firmware over the air is possible (esp32.Partition and two app slots) but is more work; for devices you can reach, USB is simpler.

A safe way back in

Keep a way to stop main.py from running: e.g. if a particular pin is held low at boot, skip it and leave the REPL free. One day an update will put the device in a reset loop, and this saves erasing it.

Logging you can read

Print statements only reach a connected USB cable. For a deployed device, publish important events (boot, errors, the reset cause) to a .../log topic at QoS 0, and keep them short. Don't write logs to flash continuously: it wears out.

From the Pi

On jarvis, systemd restarts a crashed service and the journal keeps the logs. On the ESP32, the watchdog is your Restart=always and an MQTT log topic is your journal.

Trap

Feeding the watchdog from a machine.Timer callback "so it never resets by accident". Then it never resets when it should either: the timer keeps feeding while the main loop is hung.

Try it

Add a 20 s watchdog to a loop, then put a while True: pass in the loop on the tenth cycle. Check that the board resets and that the next boot publishes WDT_RESET.
