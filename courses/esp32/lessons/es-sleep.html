A board on USB power can stay awake. A board on a battery must sleep almost all the time and wake only to measure and send. Deep sleep is how; it changes how the program is written.

Deep sleep is a reset

import machine
# ... measure, connect, publish ...
machine.deepsleep(10 * 60 * 1000)      # 10 minutes; nothing after this runs

In deep sleep almost everything is off: CPU, RAM, Wi-Fi. Waking is a reset: boot.py and main.py run from the top, every variable is gone. So a battery device's main.py isn't a loop; it's a script that runs once per wake and ends in deepsleep.

if machine.reset_cause() == machine.DEEPSLEEP_RESET:
    print("woke from sleep")
else:
    print("power-on or reset button")

Remembering across sleeps

A few bytes survive in the RTC's memory: machine.RTC().memory(b"...") to write, .memory() to read. Enough for a counter or the last value sent (to publish only on change). Gone on a power cut; for that, NVS or a file, written rarely.

What wakes it

  • A timer: the deepsleep(ms) argument.
  • A pin: esp32.wake_on_ext0(pin, level) for one RTC-capable pin (a door contact, a button), wake_on_ext1 for several.
  • Both at once: wake every hour or when the door opens, whichever is first.

Where the battery goes

Waking is cheap; Wi-Fi isn't. Joining a network takes one to several seconds at 100 mA or more, and that dominates the budget. Ways to spend less:

  • Wake often, send rarely: measure every 10 minutes, keep the last value in RTC memory, connect only when it changed or an hour has passed.
  • Connect fast: a fixed IP instead of DHCP saves time; so does a strong signal.
  • Choose the board for it: a dev board's regulator, USB chip and LED draw milliamps through the whole sleep (see the power lesson). A board built for batteries, or ESPHome on one, sleeps at tens of microamps.

MQTT for a sleeper

A device that's asleep 99% of the time can't hold a connection. Every wake is a fresh CONNECT. Its readings should be retained, so a dashboard sees the last one between wakes. Its will doesn't mean much: it publishes "offline" every time it sleeps, cleanly or not. Better: a retained timestamp in each reading, and "offline" judged from its age. Commands to it need a persistent session and QoS 1, or for it to ask on wake (the MQTT course's NATS-to-sleeping-device drill).

From MQTT

The status pattern from the MQTT course assumes an always-on client. A sleeper breaks it, which is the general lesson: the will says "connection dropped", not "device broken". Decide what "offline" means for each device.

Trap

Putting the board to sleep before the MQTT publish has actually gone out. publish() at QoS 0 writes to a socket; sleeping at once can cut it off. Disconnect cleanly first, or publish at QoS 1 and wait for the ack.

Try it

Write a main.py that counts wakes in RTC memory, prints the count, and sleeps 20 s. Then add publishing only on every third wake.
