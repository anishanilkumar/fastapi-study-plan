The house's broker is already running: NATS, with the hub on the VPS and a leaf node on jarvis. The NATS server speaks MQTT too, so devices will connect to the leaf over MQTT and their messages become NATS subjects that your programs, at home or on the VPS, can subscribe to. This lesson is what switching that on means, and what's different from a plain MQTT broker.

Switching it on

MQTT is a block in the server's config. On jarvis it goes into the hand-written config in pinix/modules/nats.nix:

mqtt {
  port: 1883            # its own listener; the client port stays on 127.0.0.1
  js_domain: home       # keep MQTT's sessions and retained values on the Pi
}

The mqtt listener has its own host, 0.0.0.0 by default, separate from the client port's host: 127.0.0.1. So it's reachable from the home network the moment it's on, and needs a login (next lesson) and a firewall rule in modules/networking.nix that opens 1883 to the home network only.

It needs JetStream

Everything MQTT must remember, NATS keeps in JetStream streams it creates and manages itself: sessions (subscriptions and queued messages), QoS 1 and 2 messages until they're acknowledged, and retained values. That's why it survives a restart. jarvis has JetStream in its own domain, home; js_domain: home makes MQTT use that one, so devices keep their sessions and retained values on the Pi, and the house keeps working when the internet is down.

Topics become subjects

MQTTNATS subject
home/kitchen/fridge/temphome.kitchen.fridge.temp
home/+/fridge/temphome.*.fridge.temp
home/kitchen/#home.kitchen.> and home.kitchen (two subscriptions)
sensor/v1.2/temp (a dot inside a level)sensor.v1//2.temp
/home/temp (leading slash)/.home.temp

So a Python program on the VPS can nats sub 'home.kitchen.>' and see what the fridge publishes. Leaf nodes only forward a subject where someone is interested, so a chatty sensor's messages cross the tailnet only when something on the hub subscribes to them.

What's different from Mosquitto

  • 3.1.1 only. A client asking for MQTT 5 is refused with CONNACK code 1. Set every client and device to 3.1.1.
  • QoS 0, 1 and 2 are all supported since NATS 2.10. A broker setting can refuse or downgrade QoS 2 if a device misbehaves with it.
  • Messages from NATS clients reach MQTT subscribers at QoS 0, whatever QoS they subscribed with. A command published with nats pub or nats-py to an offline device is lost even if the device has a persistent session. Commands that must wait for a device are published over MQTT at QoS 1.
  • Retained values are an MQTT thing. An MQTT subscriber gets them on subscribe; a plain NATS subscriber sees only live messages.
  • Client IDs must be usable as a subject token: letters, digits, - and _ are safe. A second connection with the same ID evicts the first, as on any broker.
  • Permissions are on the converted subject. A device allowed home/kitchen/fridge/# needs subscribe permission on both home.kitchen.fridge.> and home.kitchen.fridge. Servers before 2.12.3 also need $MQTT.sub.> in the subscribe allow list, or QoS 1 subscriptions fail.
From NATS

Nothing about the hub, the leaf or the existing subjects changes. MQTT is one more way in to the same subject space, with its own rules for QoS and memory on top. Keep device topics under their own prefix (home.>) so they never collide with notify.* or status.*.

Trap

Assuming a NATS program can command a device the way an MQTT client can. It can publish, but at QoS 0 and never retained: fine for "turn on now" to a device that's online, wrong for anything that must arrive later.

Try it

On your Mac, run a throwaway server: nats-server -js -c m.conf with mqtt { port: 1883 } and server_name: test in m.conf. Publish with mosquitto_pub -t home/kitchen/temp -m 4 and watch it arrive in nats sub 'home.>'. Then nats pub home.kitchen.temp 5 and watch it in mosquitto_sub -t 'home/#' -v.
