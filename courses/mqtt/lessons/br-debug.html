MQTT problems are quiet: nothing errors, messages just don't arrive. Debugging is mostly watching the broker and knowing which symptom points at which cause.

Watch everything

mosquitto_sub -h jarvis -u admin -P … -t '#' -v              # every topic, with its name
mosquitto_sub -h jarvis -t 'home/#' -v -F '%I %r %t %p'      # time, retained flag, topic, payload
mosquitto_sub -h jarvis -t 'home/#' -v --retained-only       # just the stored state, then exit
nats sub 'home.>'                                            # the same traffic as NATS subjects, on jarvis

Start every investigation here. If the device's message shows up, the problem is the subscriber; if it doesn't, the device or its permissions.

Symptoms and causes

SymptomUsually
Connects, disconnects every few seconds, foreverTwo clients with the same client ID evicting each other
Worked until the first Wi-Fi blip, then receives nothingSubscribed outside the connected callback; clean session lost the subscription
Disconnected after about a minute of quietA blocking callback stopped the loop, so no keepalive pings
Connection refused, code 1The client asked for MQTT 5; the broker speaks 3.1.1
Connection refused, code 4 or 5Wrong password, or the user isn't allowed MQTT connections
Publishes, nobody gets itNo permission to publish there (often dropped silently), a typo or case difference in the topic, or a leading /
A dashboard shows a value from last weekA stale retained message; or a will that wasn't retained
A device turns itself off on every rebootA retained command on its /set topic
Commands sent while a device slept never arriveClean session, QoS 0, or sent from a NATS client (always QoS 0)
Every message arrives twiceTwo overlapping subscriptions in one client (home/# and home/kitchen/#): the spec lets a broker send a copy for each. Or QoS 1 redelivery (look for the DUP flag)

Clearing a stuck retained message

mosquitto_sub -h jarvis -t 'home/#' -v --retained-only      # find it
mosquitto_pub -h jarvis -t home/hall/light/power/set -r -n  # an empty retained message deletes it

Watching the server

On jarvis, the monitoring port is 127.0.0.1:8222: curl -s 127.0.0.1:8222/connz lists connections (MQTT ones included, with their client IDs), /varz the server, /leafz the link to the hub, /jsz JetStream, where MQTT's state lives. The server's log (journalctl -u nats) shows refused connections and permission violations, which the client usually never hears about.

When it's the network

A device that drops off regularly is often Wi-Fi: check its signal (Tasmota reports RSSI in tele/.../STATE; Zigbee2MQTT reports linkquality). Lower its keepalive a little so it's noticed sooner, and make sure it reconnects with backoff rather than hammering.

From HTTP

An HTTP failure is a status code at the caller. An MQTT failure is usually an absence, so you look at the middle: the broker sees every connection, publish and refusal. Its log and a # subscription are your access log.

Trap

Leaving a debugging mosquitto_sub -t '#' running under a persistent session (-c). When it's closed, the broker keeps queueing every QoS 1 message in the house for it.
