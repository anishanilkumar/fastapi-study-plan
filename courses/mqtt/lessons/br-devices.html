Most devices in a house won't run your code. They run firmware that already speaks MQTT, each with its own topic scheme. Learn to read them, and the broker becomes one place to see and drive all of them.

Tasmota (Wi-Fi plugs and switches)

cmnd/hall-plug/POWER       ON          # you send commands here
stat/hall-plug/POWER       ON          # it answers with the result
tele/hall-plug/STATE       {...}       # periodic state, every TelePeriod seconds
tele/hall-plug/SENSOR      {"ENERGY": {"Power": 412, ...}}
tele/hall-plug/LWT         Online      # retained; Offline is its last will

Three prefixes: cmnd (in), stat (answers), tele (telemetry). The middle part is the device's topic, set in its web UI. tele/+/LWT is the list of every Tasmota device and whether it's up.

ESPHome (your own ESP32 boards)

ESPHome devices usually talk to Home Assistant over its native API, not MQTT. Add an mqtt: block to the YAML and they publish under a prefix instead:

mqtt:
  broker: 192.168.1.20        # jarvis on the LAN
  username: fridge
  password: !secret mqtt_password
  topic_prefix: home/kitchen/fridge

# publishes  home/kitchen/fridge/sensor/temperature/state   4.2
# birth/will home/kitchen/fridge/status                      online / offline (retained)
# commands   home/kitchen/fridge/switch/fan/command          ON

Here you choose the scheme, so make it match your own (lesson 2).

Zigbee2MQTT (Zigbee sensors through a USB stick)

zigbee2mqtt/bridge/state                 online          # the bridge itself, retained
zigbee2mqtt/hall-door                    {"contact": false, "battery": 97, "linkquality": 120}
zigbee2mqtt/hall-lamp/set                {"state": "ON", "brightness": 180}

One JSON object per device, named by its friendly name; commands go to <name>/set. A Zigbee door sensor is battery-powered and sleeps, so it only reports on change: its last value is all you have, which is why Zigbee2MQTT can retain it.

Home Assistant discovery

Home Assistant finds MQTT devices from config messages, retained, under homeassistant/:

topic:   homeassistant/sensor/fridge_temp/config         (retained)
payload: {"name": "Fridge", "unique_id": "fridge-temp-a4cf12",
          "state_topic": "home/kitchen/fridge/sensor/temperature/state",
          "unit_of_measurement": "°C", "device_class": "temperature",
          "availability_topic": "home/kitchen/fridge/status"}

It's retained so Home Assistant sees it whenever it starts. Home Assistant publishes online to homeassistant/status when it starts; a device that sees that should publish its config again, in case the retained copy is gone. ESPHome, Tasmota and Zigbee2MQTT can all do discovery for you. To remove a device, publish an empty retained message to its config topic.

On the NATS broker

All of these default to MQTT 3.1.1 or let you choose it; check, since some newer integrations pick 5 by default. Their client IDs (DVES_A4CF12, esphome-fridge) are fine as subject tokens. Their topics become subjects: tele/hall-plug/SENSOR is tele.hall-plug.SENSOR to a NATS program.

From HTTP

Each of these also has a web UI or an HTTP API. Use MQTT for anything automated: it's one connection, it's pushed when something changes, and the broker tells you when the device goes away.

Trap

A retained discovery config left behind after renaming a device. Home Assistant keeps showing the old entity as unavailable, forever. Clear the old config topic with an empty retained publish.
