Everything a client is to the broker is decided in its first packet, CONNECT. Most "it connects but then something weird happens" bugs come from one of its fields.

What CONNECT carries

FieldWhat it does
Client IDWho this is. The broker keys the session by it (lesson 5). One per device, stable across reboots.
Clean sessionIn 3.1.1: true throws away any stored session now and at disconnect; false resumes it.
KeepaliveSeconds between packets the client promises (lesson 1). 0 turns it off; don't.
Username / passwordSent as plain bytes. Without TLS, anyone on the path can read them.
WillA message the broker publishes for you if you vanish (lesson 6).

The answer: CONNACK

In 3.1.1 the broker answers with a return code. Know them; client libraries often only log the number.

CodeMeaning
0Accepted
1Unacceptable protocol version (a client asking for MQTT 5 on a broker that only speaks 3.1.1, like NATS)
2Client identifier rejected
3Server unavailable
4Bad username or password
5Not authorised

CONNACK also says whether a stored session was found ("session present"). A client that asked to resume and gets session present = 0 must subscribe again: the broker has forgotten its subscriptions.

Client IDs: one connection each

If a second connection arrives with a client ID already connected, the broker disconnects the first one. Two devices flashed with the same ID, or a script run twice, then knock each other off in a loop: each reconnects, evicts the other, and both log "connection lost" every few seconds. Build the ID from something unique and stable (fridge-sensor-a4cf12 from the MAC address), and give each running program its own.

import socket, os
client_id = f"pantry-bridge-{socket.gethostname()}"   # stable, unique per machine
# random each start (uuid4) is fine only with clean_session=True:
# a persistent session under a fresh id is never resumed, just left behind

Reconnecting

Networks drop. A client must reconnect by itself, with a growing delay (1 s, 2 s, 4 s … up to a minute or two) so that fifty devices coming back after a power cut don't all hammer the broker in the same second. And after every reconnect it must subscribe again unless the session was resumed. The simplest correct habit: subscribe inside the "connected" callback, every time.

From HTTP

An HTTP client authenticates on every request and a dead server is an immediate error. An MQTT client authenticates once, then sits on a connection that can die silently. So the work moves: keepalive to notice, reconnect logic to recover, and resubscribing to restore what the connection meant.

Trap

Subscribing once, right after connect(), outside the connected callback. It works on your desk. After the first Wi-Fi blip the client reconnects with a clean session and silently receives nothing ever again.

Try it

Run mosquitto_sub -h test.mosquitto.org -i anish-same -t 'anish-test/#' -v in two terminals with the same -i. Watch them take turns being disconnected. Then run them with different IDs.
