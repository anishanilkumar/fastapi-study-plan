Two features turn MQTT from a stream of events into something that knows the current state of the house: retained messages, and the last will.

Retained: the last known value

Publish with the retain flag and the broker keeps that message as the topic's current value, one per topic. Anyone who subscribes later gets it straight away, then the live updates.

mosquitto_pub -t home/kitchen/fridge/temp -m 4.2 -r     # kept
mosquitto_sub -t 'home/kitchen/#' -v                    # a minute later: gets 4.2 at once
  • A new retained message on the topic replaces the old one. Only the last is kept.
  • It's kept per topic name, not per filter: a subscriber to home/# gets the retained value of every topic below.
  • To delete it, publish an empty retained message to the topic: mosquitto_pub -t home/kitchen/fridge/temp -r -n. Publishing a non-retained message does not clear it.
  • A retained message delivered on subscribe has its retain flag set, so a subscriber can tell "this is old state" from "this just happened".

What to retain

State, not events. "The heater is on", "the fridge is 4.2 °C", "the device is online": retain. "The doorbell was pressed", "a label was printed": don't, or every dashboard that connects tomorrow rings the bell again. And never retain a command: a retained .../set off turns the device off again every time it reconnects, long after anyone wanted that.

The last will

In CONNECT a client can leave a will: a topic, a payload, a QoS and a retain flag. If the client disappears without saying goodbye (keepalive timed out, network dropped, protocol error), the broker publishes the will for it. A clean DISCONNECT discards it.

The status pattern

Together they give every device an online/offline topic that's always right:

1. CONNECT with will:  home/kitchen/fridge/status = "offline", retained, QoS 1
2. once connected:     publish home/kitchen/fridge/status = "online", retained, QoS 1
3. shutting down:      publish "offline" (retained) yourself, then DISCONNECT

Step 2 is the "birth" message; step 1 covers the crash; step 3 covers the clean exit, where the will doesn't fire. A dashboard subscribing to home/+/+/status immediately sees every device's state, even one that died an hour ago. Tasmota, ESPHome and Zigbee2MQTT all do exactly this.

From HTTP

An HTTP health check polls: "are you there?" every few seconds. The will turns it around: the broker already knows when a connection dies, so it announces it once, and the retained flag keeps the answer for anyone who asks later.

Trap

A will that isn't retained. It's published once, to whoever happens to be subscribed at that moment, and the retained "online" from the birth message stays the topic's value. The dashboard says the dead device is fine, forever.

Try it

mosquitto_sub -h test.mosquitto.org -t 'anish-test/dev/status' -v --will-topic anish-test/dev/status --will-payload offline --will-retain -k 5, then kill the terminal (don't Ctrl-C cleanly). From another terminal subscribe to the topic after ten seconds.
