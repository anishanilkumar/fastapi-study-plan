A topic is a UTF-8 string split into levels by /. The broker never stores a list of topics: it matches each published topic against each subscription's filter. Getting the names right is most of designing an MQTT system, and the hardest part to change later, because every device and dashboard has them hard-coded.

Levels and the two wildcards

home/kitchen/fridge/temp          # a topic: 4 levels
home/+/fridge/temp                # + : exactly one level
home/kitchen/#                    # # : this level and everything below, last only
#                                 # everything (except $-topics)
  • + matches exactly one whole level: home/+/temp matches home/kitchen/temp, not home/kitchen/fridge/temp.
  • # must be the last character, and matches the parent too: home/kitchen/# matches home/kitchen itself.
  • Wildcards are for subscribing only. Publishing to home/+/temp is a protocol error and the broker drops the connection.
  • A wildcard is a whole level: home/kit+ is invalid, not a prefix match.

Rules that bite

  • Case matters. Home/Kitchen and home/kitchen are different topics.
  • No leading slash. /home/kitchen has an empty first level, so home/# doesn't match it. Pick no slash and stick to it.
  • No spaces and no odd characters, even where the spec allows them: some brokers (NATS among them) refuse whitespace, and every shell command gets harder.
  • $ topics are the broker's. $SYS/... on Mosquitto carries broker statistics. A filter starting with a wildcard (#, +/...) never matches them; subscribe to $SYS/# explicitly.

A naming scheme that lasts

<site>/<room>/<device>/<what>       home/kitchen/fridge/temp
                                     home/kitchen/fridge/status   (online / offline)
<site>/<room>/<device>/<what>/set   home/hall/light/power/set    (a command)

General to specific, left to right, so the useful wildcards fall out: one room (home/kitchen/#), one measurement everywhere (home/+/+/temp), one device (home/kitchen/fridge/#). Keep commands on their own topic (.../set) and the device's reported state on the plain topic, so a dashboard never mistakes a request for a fact. Device firmware often brings its own scheme (Tasmota's cmnd/, stat/, tele/, Zigbee2MQTT's zigbee2mqtt/<name>); lesson 14 covers them. Don't fight those; keep your own programs consistent.

What goes in a level

Stable identifiers, not display names or values. home/kitchen/fridge, not home/Kitchen Fridge (new). And never put data in the topic that belongs in the payload: home/kitchen/fridge/temp/4.2 creates a new topic for every reading and makes retained values and subscriptions useless.

From NATS

Same idea, different punctuation: home/kitchen/# is home.kitchen.>, home/+/temp is home.*.temp. One difference: MQTT's # also matches the parent level (home/kitchen), NATS's > doesn't. When NATS speaks MQTT it converts between them for you, and has to subscribe twice to cover # (lesson 12).

Trap

Subscribing to # in a program "to see everything" and filtering in code. It's fine for debugging, but in production every message on the broker crosses the network to you, including camera snapshots someone later publishes. Subscribe to what you need.

Try it

For each filter, say which of home/kitchen, home/kitchen/temp, home/hall/light/power, /home/kitchen/temp it matches: home/#, home/+, home/+/temp, +/+/+, home/kitchen/#.
