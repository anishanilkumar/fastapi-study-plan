aiomqtt wraps paho in asyncio: no callbacks, no threads, just async with and async for. It's the natural fit inside a FastAPI app or any program that already runs an event loop.

Subscribe and handle

import asyncio, aiomqtt

async def main():
    async with aiomqtt.Client("jarvis", username="fridge-logger", password=PW,
                              identifier="fridge-logger-mac", keepalive=60) as client:
        await client.subscribe("home/kitchen/fridge/#", qos=1)
        async for message in client.messages:
            if message.topic.matches("home/kitchen/fridge/temp"):
                print("temp", float(message.payload))
            elif message.topic.matches("home/+/+/status"):
                print(message.topic.value, message.payload.decode())

asyncio.run(main())

message.topic is a Topic object: .value is the string, .matches(filter) applies MQTT's wildcard rules for you. message.payload is bytes. In aiomqtt 2, client.messages is an async iterator you loop over directly; older 1.x examples wrote async with client.messages() as messages:.

It doesn't reconnect: you do

When the connection drops, the async for raises aiomqtt.MqttError and the async with exits. There's no automatic reconnect, by design: you write the loop, so you decide the delay and what to redo.

async def run():
    delay = 1
    while True:
        try:
            async with aiomqtt.Client("jarvis", identifier="fridge-logger-mac") as client:
                delay = 1                                  # connected: reset the backoff
                await client.subscribe("home/kitchen/fridge/#", qos=1)
                async for message in client.messages:
                    await handle(message)
        except aiomqtt.MqttError as e:
            log.warning("mqtt lost (%s); retrying in %d s", e, delay)
            await asyncio.sleep(delay)
            delay = min(delay * 2, 60)

Subscribing is inside the loop, so every new connection subscribes again: the same rule as paho's on_connect.

Slow handlers

Messages are handled one at a time in that async for. An await in handle is fine for anything quick; a blocking call is not, for the usual reason: it stalls the event loop, and with it the keepalive. For work that can run alongside, start a task per message with a bound on how many run at once (an asyncio.Semaphore), or put messages on an asyncio.Queue for a few workers.

Inside FastAPI

from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    task = asyncio.create_task(run())      # the reconnect loop above
    yield
    task.cancel()                          # shutdown: leave the broker cleanly

app = FastAPI(lifespan=lifespan)

To publish from a route, keep one connected client on app.state and await client.publish("home/hall/light/power/set", "ON", qos=1). Don't open a new MQTT connection per HTTP request: each is a TCP and TLS handshake, a CONNECT, and a fight over the client ID if they share one.

From FastAPI

The same lifespan you used for an httpx.AsyncClient: create the long-lived thing once at startup, share it, close it at shutdown. The MQTT client is just another one.

Trap

Two parts of one program each opening an aiomqtt.Client with the same identifier. They evict each other every few seconds, and both reconnect loops make it look like a flaky network.
