paho-mqtt is the standard Python client, from the Eclipse project that also makes Mosquitto. It's callback-based and runs its network loop in a thread. Version 2 (2024) changed the callback signatures, so many examples online no longer run as written.

A complete subscriber

import json, logging
import paho.mqtt.client as mqtt

log = logging.getLogger("fridge")

def on_connect(client, userdata, flags, reason_code, properties):
    if reason_code.is_failure:
        log.error("connect refused: %s", reason_code)      # e.g. "Not authorized"
        return
    # Here, not after connect(): this runs again after every reconnect.
    client.subscribe("home/kitchen/fridge/#", qos=1)

def on_message(client, userdata, msg):
    log.info("%s %r retained=%s", msg.topic, msg.payload, msg.retain)

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="fridge-logger-mac",
                     protocol=mqtt.MQTTv311)
client.username_pw_set("fridge-logger", password)
client.on_connect = on_connect
client.on_message = on_message
client.reconnect_delay_set(min_delay=1, max_delay=60)
client.connect("jarvis", 1883, keepalive=60)
client.loop_forever()          # blocks; reconnects by itself

The first argument, CallbackAPIVersion.VERSION2, picks the new callback signatures: on_connect gets a reason_code object and properties. Leave it out and paho 2 complains; old examples with on_connect(client, userdata, flags, rc) are the version 1 API.

The loop: who runs your callbacks

CallWhat it does
loop_forever()Runs the network loop in this thread, until disconnect(). For a program that only reacts to messages.
loop_start() / loop_stop()Runs it in a background thread, so your own code keeps going. Callbacks then run in that thread.

The same thread that runs your callbacks also sends the keepalive pings and reads the socket. A callback that blocks (an HTTP call, a time.sleep, a slow database write) stops all of that: no other messages are handled, and long enough, the broker decides you're dead. Keep callbacks short; hand slow work to a queue.Queue and a worker thread.

Publishing

client.loop_start()
info = client.publish("home/kitchen/fridge/temp", "4.2", qos=1, retain=True)
info.wait_for_publish(timeout=5)       # for QoS 1: until the broker's PUBACK
if not info.is_published():
    log.warning("not acknowledged yet; paho will retry")

publish() returns at once; the message goes out from the loop thread. In a short script that publishes and exits, call wait_for_publish() or the process can end before anything was sent. Payloads can be str (sent as UTF-8), bytes, or numbers; send JSON as json.dumps(...).

Last will and a clean exit

client.will_set("home/kitchen/fridge/status", "offline", qos=1, retain=True)
client.connect("jarvis", 1883, keepalive=60)
...
client.publish("home/kitchen/fridge/status", "offline", qos=1, retain=True).wait_for_publish()
client.disconnect()                    # clean: the will is not sent

will_set must come before connect: the will is part of CONNECT.

From FastAPI

A FastAPI handler returns and the request is done. A paho callback returns into a loop that must keep spinning. It's the same lesson as "one blocking call stalls the event loop", with a thread instead of an event loop.

Trap

An exception raised inside a callback. By default paho logs it and raises it again out of the network loop: loop_forever() ends, or with loop_start() the background thread dies and the client quietly stops receiving while the rest of the program runs on. Catch and log in your own handler, with the topic and payload. (client.suppress_exceptions = True makes paho only log it; turn on client.enable_logger() to see that.)
