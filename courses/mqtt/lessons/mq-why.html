MQTT is a publish/subscribe protocol for small devices on unreliable networks. A sensor doesn't call a server; it publishes a message to a topic on a broker, and whoever has subscribed to that topic gets a copy. The sensor never knows who that is, or whether anyone is listening.

The three pieces

  • Broker. The one server everything connects to. It keeps the connections, matches each published message against the subscriptions and delivers copies. At home, that will be the NATS leaf on jarvis (Mosquitto is the other common one).
  • Clients. Everything else: an ESP32 with a temperature sensor, a Zigbee bridge, Home Assistant, a Python script. Every client can publish and subscribe; "sensor" and "dashboard" are only roles.
  • Topics. Strings like home/kitchen/fridge/temp. There's nothing to create first: publishing to a topic is enough for it to exist, for that one message.

What one exchange looks like

fridge sensor  ── CONNECT ───────────────▶ broker
               ◀─ CONNACK (accepted) ────
               ── PUBLISH home/kitchen/fridge/temp "4.2" ─▶
                                                   │ matches "home/+/fridge/#"
dashboard      ◀───────────────────── PUBLISH ─────┘

Every packet goes over one long-lived TCP connection per client (port 1883 plain, 8883 with TLS). The client opens it, so a device behind NAT needs no open port: it dials out, and the broker pushes messages down that same connection. The fixed header is two bytes; a whole small publish is a few dozen. That's why a battery device can afford it.

Keepalive: how the broker knows you're gone

The client says in CONNECT how often it will be heard from, e.g. 60 seconds. If it has nothing else to send in that time it sends a two-byte PINGREQ, and the broker answers PINGRESP. If the broker hears nothing for one and a half times the keepalive, it treats the client as dead, closes the connection and (lesson 6) publishes its last will. TCP alone can take many minutes to notice a device that lost power; keepalive bounds it.

When MQTT is the right tool

UseFor
MQTTDevices you don't write the firmware for (Tasmota, ESPHome, Zigbee2MQTT, Home Assistant all speak it), small boards, battery, flaky Wi-Fi
NATS (core, JetStream)Your own programs: the household's notify.*, print.queued, request/reply, streams and work queues
HTTPAsking a server for a page or a resource; anything with a request and an answer you wait for

You don't have to pick one: the NATS server speaks MQTT too, so a message a device publishes over MQTT can reach a Python program subscribed with a NATS client, and the other way round. Lesson 12 is about exactly that.

From HTTP

HTTP is request/response: the client asks, a named server answers, and the connection is often closed after. MQTT is the opposite shape: connections stay open, nobody is addressed by name, and the publisher gets no answer from subscribers, only (at QoS 1 and 2) an acknowledgement from the broker. "Did the light turn on?" is a second message the light publishes, not a response.

From NATS

You already know this model: subjects, wildcards, publishers that don't know their subscribers. MQTT topics use / where NATS uses ., and +/# where NATS uses */>. What MQTT adds is built for devices: per-message QoS, sessions that survive a disconnect, retained values and a last will.

Trap

"Published" doesn't mean "received". At QoS 0 a message to a topic nobody subscribes to is simply dropped, with no error. Even at QoS 1, the acknowledgement comes from the broker, not from any subscriber.

Try it

With Mosquitto's command-line tools (nix shell nixpkgs#mosquitto) and the public test broker: in one terminal mosquitto_sub -h test.mosquitto.org -t 'anish-test/#' -v, in another mosquitto_pub -h test.mosquitto.org -t anish-test/hello -m hi. Then publish before subscribing and see that the message is gone. Never send anything private to a public broker.
