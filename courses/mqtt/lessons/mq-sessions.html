QoS only protects a message while the subscriber is connected, unless the broker keeps a session for it. A session is the broker remembering a client between connections. It's what lets a device sleep, or lose Wi-Fi for ten minutes, and still get the commands sent meanwhile.

What a session holds

  • The client's subscriptions, so it needn't send SUBSCRIBE again.
  • QoS 1 and 2 messages that matched those subscriptions while the client was away, queued for it.
  • QoS 1 and 2 messages in flight when the connection dropped, not yet acknowledged.

QoS 0 messages are never queued for an offline client. A persistent session doesn't change that.

Clean session, in 3.1.1

clean_session = True    # start empty; forget everything at disconnect
clean_session = False   # resume the session for this client ID, keep it after

With False, the session lives under the client ID, so the ID must be stable (lesson 3). Reconnect under the same ID and the queued messages arrive, and CONNACK says session present = 1.

Choosing

ClientSessionWhy
A dashboard, a debugging mosquitto_subCleanOnly the current state matters; retained messages (next lesson) give it that at connect
A device that receives commandsPersistent, subscribe at QoS 1"Heater off" sent while it rebooted must still arrive
A program that logs every event to a databasePersistent, QoS 1No gaps when it restarts for a deploy

Sessions cost the broker

A persistent session for a client that never comes back keeps queueing forever, or until the broker's own limit. In 3.1.1 there's no expiry in the protocol; brokers add their own (Mosquitto's persistent_client_expiration, for one). MQTT 5 fixes this with a session expiry interval (lesson 8). So: persistent sessions only for clients that will return, under IDs that don't change, and connect once with clean session True to delete one you've retired.

A queue is not a history

A session delivers what was published after the session existed. A client that connects for the first time gets nothing from before, except retained messages. If a program needs past events (yesterday's readings), that's a database's job, or a JetStream stream's, not MQTT's.

From NATS

A persistent MQTT session is close to a durable JetStream consumer: named, it remembers where you got to and redelivers unacknowledged messages. NATS in fact keeps MQTT sessions in JetStream, so they survive a server restart.

Trap

A persistent session with a random client ID per start. Every restart makes a new session that's never resumed, and the broker keeps queueing for all the old ones.

Try it

Subscribe with mosquitto_sub -c -i anish-sess -q 1 -t 'anish-test/cmd' -h test.mosquitto.org (-c is clean session off), stop it, publish three messages at -q 1, start it again. Then repeat with -q 0 on the publish.
