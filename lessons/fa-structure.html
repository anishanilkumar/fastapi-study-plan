How a real FastAPI project is laid out, configured and run. Useful for the project deep-dive and for reading an unfamiliar codebase quickly.

Routers

# app/routers/devices.py
router = APIRouter(prefix="/devices", tags=["devices"],
                   dependencies=[Depends(current_user)])

@router.get("/{device_id}")
def get_device(device_id: int): ...

# app/main.py
app = FastAPI(lifespan=lifespan)
app.include_router(devices.router)
app.include_router(admin.router)

Like route groups / controllers. Tags group endpoints in /docs.

Layers

  • routers/: HTTP only. Parse, call a service, map errors to status codes.
  • schemas.py: Pydantic in/out models.
  • models.py: SQLAlchemy tables.
  • services/ (optional): business logic that doesn't know about HTTP, so it's testable alone.
  • db.py, config.py, deps.py: engine and get_db, settings, shared dependencies.

Settings

from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    database_url: str
    secret_key: str
    debug: bool = False
    model_config = SettingsConfigDict(env_file=".env")

settings = Settings()        # reads env vars; fails at startup if one is missing

Failing at startup on missing config is a feature: better than discovering an empty secret at the first request.

Middleware

@app.middleware("http")
async def add_request_id(request: Request, call_next):
    rid = request.headers.get("X-Request-Id") or uuid.uuid4().hex
    response = await call_next(request)
    response.headers["X-Request-Id"] = rid
    return response

Migrations

Alembic is SQLAlchemy's migration tool: alembic revision --autogenerate -m "add serial", review the generated file, alembic upgrade head. Never rely on Base.metadata.create_all() in production; it doesn't alter existing tables.

Running in production

fastapi run app/main.py --workers 4
# or
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
  • Behind nginx or a load balancer that terminates TLS; pass --proxy-headers so the app sees the real scheme and client IP.
  • Each worker is a separate process with its own memory (see the long-running process lesson).
  • In containers, often one worker per container and let the orchestrator scale.
  • A /health endpoint that doesn't touch slow dependencies.
From PHP

config/*.php + .env → BaseSettings. Laravel migrations → Alembic. nginx + PHP-FPM pool → nginx + uvicorn workers; pm.max_children ≈ --workers (but each worker serves many requests concurrently).
