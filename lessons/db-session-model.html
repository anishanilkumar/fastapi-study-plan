Transactions, isolation and constraints you know. What's new is the layer on top: in Drupal, $entity->save() writes right away; in SQLAlchemy you change objects, nothing is sent, and the Session decides when the SQL goes out. This lesson shows exactly when, line by line. Once that's clear, the rules in the next lesson (one session per request, roll back after errors) follow from it.

See the SQL: turn on echo

engine = create_engine("sqlite:///test.db", echo=True)   # logs every statement
SessionLocal = sessionmaker(engine)                       # a factory, configured once

Do every example below with echo=True. Watching when SQL goes out is the fastest way to learn this. sessionmaker is just a configured way to make sessions: SessionLocal() is a new one.

The session is a unit of work

A session sits in front of one database transaction and collects changes. It sends them (flush) when it needs to, and ends the transaction (commit) when you say so. Three things it keeps:

  • A transaction. Opened on the first statement (it borrows a connection from the engine's pool), ended by commit() or rollback().
  • The pending changes. New objects you add(), attributes you set on loaded objects, objects you delete().
  • An identity map. One Python object per database row: load row 5 twice in a session and you get the same object back, with no second query. Drupal's entity static cache does the same within a request.

Step by step, with the SQL

with SessionLocal() as session:            # no connection, no SQL yet
    d = Device(serial="A-1", owner_id=1)  # a plain object: the session doesn't know it
    session.add(d)                         # now it does ("pending"). Still no SQL
    print(d.id)                            # None: nothing has been inserted

    session.flush()                        # BEGIN
                                           # INSERT INTO devices (serial, owner_id) VALUES (?, ?)
    print(d.id)                            # 7: the row exists, inside the transaction

    d.note = "rack 3"                      # tracked. No SQL
    same = session.get(Device, 7)          # identity map: no SQL, and same is d

    rows = session.scalars(select(Device).where(Device.note == "rack 3")).all()
                                           # autoflush first: UPDATE devices SET note=? WHERE id=?
                                           # then the SELECT, which finds d

    session.commit()                       # COMMIT. Now it's visible to other connections
    print(d.note)                          # BEGIN; SELECT ... FROM devices WHERE id = 7
                                           # (reloaded: see "after commit" below)
# leaving the with block closes the session; d is now "detached"

Three things to take from this:

  • flush ≠ commit. Flush sends the SQL inside the open transaction (so you get ids, and constraint errors show up). Commit ends the transaction. Nothing is permanent until commit.
  • Autoflush. Before any query, the session flushes pending changes, so your own query sees them. That's why an IntegrityError can surface on a select, not where you called add.
  • No commit, no save. Closing a session that wasn't committed rolls back. Forgetting commit() is the classic "it returned 201 but nothing is in the table".

After commit: attributes expire

By default (expire_on_commit=True), commit() marks every loaded object as stale. The next attribute you read triggers a fresh SELECT, in a new transaction. That's deliberate: after commit, another request may have changed the row.

The trap is the next step: a detached object can't reload.

def create_device(data) -> Device:
    with SessionLocal() as session:
        d = Device(**data)
        session.add(d)
        session.commit()      # d's attributes expire here
        return d              # the session closes on the way out

d = create_device({"serial": "A-1", "owner_id": 1})
d.serial                      # DetachedInstanceError: expired, and no session to reload it

Fixes, in order of preference: do the work (or build the response) while the session is open; session.refresh(d) before closing, to load it again on purpose; or sessionmaker(engine, expire_on_commit=False), so committed objects keep their values (common with AsyncSession, where an implicit reload isn't allowed).

Lazy loading needs a live session

Relationships aren't loaded with the object. Reading d.owner the first time sends a SELECT then. That works while the session is open, and fails on a detached object with the same DetachedInstanceError. In a loop it is the N+1 problem. Two ways round it:

# load what you'll need, up front, in the same query
from sqlalchemy.orm import selectinload, joinedload
devices = session.scalars(select(Device).options(joinedload(Device.owner))).all()   # one JOINed query
owners = session.scalars(select(Owner).options(selectinload(Owner.devices))).all()  # 2 queries total

# or make a forgotten one loud instead of slow
devices = session.scalars(select(Device).options(raiseload("*"))).all()

Rule of thumb: joinedload for many-to-one (a device's owner), selectinload for one-to-many (an owner's devices).

Errors: roll back, then carry on

session.add(Device(serial="A-1", owner_id=1))   # serial already exists
try:
    session.commit()                            # flush → IntegrityError
except IntegrityError:
    session.rollback()                          # required: the transaction is dead
    raise HTTPException(409, "serial already registered")

After a failed flush, the session refuses to do anything else until you rollback() (PendingRollbackError). Rollback also discards everything pending and expires every object, because none of it is true any more.

One transaction for one job

# BUG: a commit per row. Half-done if row 40 fails; 100 transactions
for row in rows:
    session.add(Reading(**row))
    session.commit()

# one unit of work: all or nothing
with SessionLocal.begin() as session:      # commits at the end, rolls back on an exception
    session.add_all([Reading(**row) for row in rows])

SessionLocal.begin() is the short form of "open a session, begin, commit or roll back, close". In FastAPI the session comes from a dependency (next lesson); the endpoint calls commit() once, at the end.

Bulk statements skip the objects

session.execute(update(Device).where(Device.owner_id == 1).values(note="moved"))
session.execute(delete(Device).where(Device.serial.like("TEST-%")))

One SQL statement, no objects loaded, no per-row events. Use them for "change many rows" and for counters (values(stock=Product.stock - 1)), which also avoids lost updates. Objects already loaded in the session are updated to match by default.

A request, start to finish

def get_db():
    with SessionLocal() as session:   # 1. a new session for this request
        yield session                 # 2. the endpoint runs with it
                                      # 4. closed: not committed? rolled back

@app.post("/devices", status_code=201, response_model=DeviceOut)
def create(body: DeviceIn, db: Annotated[Session, Depends(get_db)]):
    d = Device(**body.model_dump())
    db.add(d)
    try:
        db.commit()                   # 3. one commit, at the end
    except IntegrityError:
        db.rollback()
        raise HTTPException(409, "serial already registered")
    return d                          # read while the session is still open
From Drupal
  • $t = $connection->startTransaction(), committed when $t goes out of scope→ with SessionLocal.begin() as session: commits at the end of the block, rolls back on an exception
  • $t->rollBack() in a catch→ session.rollback(), and it's required before the session does anything else
  • Node::create([...])→ Device(...): transient, not stored
  • $node->save(): SQL now, in its own transaction→ session.add(d), then one commit() for everything. Setting d.note is the whole "save"
  • Entity static cache; resetCache()→ The identity map; expire(), refresh()
  • $node->field_owner->entity loads on access→ Lazy loading of d.owner, with the same N+1 risk in a loop
  • loadMultiple($ids) to avoid N+1→ selectinload / joinedload
  • $connection->update('devices')->fields(...)->condition(...)→ update(Device).where(...).values(...): one statement, no objects
  • Placeholders: ->condition('serial', $serial)→ .where(Device.serial == serial)

The big difference: a Drupal request starts fresh, so the static cache and any open transaction die with it. A Python server keeps running, so a session must be opened and closed per request on purpose, or it leaks state between users.
